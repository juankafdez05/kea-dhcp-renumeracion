01

Reconocimiento del terreno El escenario

Un cliente dispone de una concesión del rango antiguo. El administrador cambia el pool y espera que, al renovar, reciba inmediatamente una dirección del nuevo rango.

Ejemplo / 172.21.0.0/24 
Pool anterior: 172.21.0.10 - 172.21.0.30
Pool nuevo:    172.21.0.40 - 172.21.0.70
IP actual:     172.21.0.20

La distinción importante: modificar el pool no envía por sí mismo una orden al cliente para abandonar su dirección actual.

El pool configurado, el registro de la concesión y el estado del cliente son elementos diferentes. No debe deducirse el resultado de una renovación únicamente mirando el nuevo rango.

Esta guía no afirma que todas las versiones de Kea renueven direcciones fuera del pool. Verifica la respuesta con tu versión, configuración y tráfico. Consulta el manual de Kea.

02

Domina los tiempos Qué significan T1 y T2

T1

RENEWING

El cliente intenta renovar con el servidor que le concedió la dirección. No está solicitando necesariamente una IP distinta.

T2

REBINDING

Si no logró renovar, amplía la petición mediante broadcast para intentar obtener una respuesta.

FIN

EXPIRACIÓN

Sin renovación, al expirar la concesión deja de utilizarla y reinicia la adquisición de configuración.

Según RFC 2131, los valores predeterminados son T1 = 50 % y T2 = 87,5 % del tiempo de concesión. Pueden especificarse otros valores. Referencia: §4.4.5.

Reducir los temporizadores del servidor no modifica retroactivamente los que un cliente ya recibió. Planifica los tiempos antes de la migración.

03

La misión, paso a paso Cambiar el pool

Ejemplo para un servidor independiente administrado mediante archivos locales y systemd. Adapta rutas, unidad y mecanismo de aplicación a tu instalación.

Antes de empezar: prepara acceso de recuperación y una ventana de mantenimiento. En HA, backends de configuración o appliances, utiliza el procedimiento de su gestor.

01 / Identifica la configuración efectiva

Confirma qué binario y archivo utiliza el proceso. El nombre de servicio siguiente es un ejemplo.

Inventario 
kea-dhcp4 -V
kea-dhcp4 -W
sudo systemctl cat kea-dhcp4-server

Revisa subredes, reservas, clases, otros pools, relays y hooks. No publiques credenciales ni configuraciones reales completas.

02 / Guarda una copia de seguridad

Copia local 
sudo cp -a /etc/kea/kea-dhcp4.conf \
  "/etc/kea/kea-dhcp4.conf.bak.$(date +%Y%m%d-%H%M%S)"

Si utilizas archivos incluidos, respalda también los que vayas a modificar. Mantén las copias fuera del repositorio público.

03 / Modifica únicamente el pool afectado

Dentro de la subred existente, cambia el atributo pool. Conserva el ID de subred y los demás atributos. No elimines otros pools necesarios.

Fragmento / no es una configuración completa 
"pools": [
  {
    "pool": "172.21.0.40 - 172.21.0.70"
  }
]

Comprueba que el rango pertenece a la subred y no contiene direcciones utilizadas estáticamente. Revisa las reservas que puedan devolver una IP antigua.

Para configuraciones compatibles también puedes utilizar la herramienta Python de esta guía.

04 / Valida antes de aplicar

Validación 
sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf

Utiliza el mismo binario que ejecuta el servicio. Si la validación falla, no continúes. Superarla no demuestra que el proceso activo haya cargado el cambio ni que la migración funcione.

05 / Aplica y comprueba

Este ejemplo reinicia el servicio y puede interrumpir temporalmente DHCP. Sustituye la unidad por la real.

Ventana de mantenimiento 
sudo systemctl restart kea-dhcp4-server
sudo systemctl status kea-dhcp4-server --no-pager -l
sudo journalctl -u kea-dhcp4-server \
  --since "5 minutes ago" --no-pager

06 / Migra y verifica los clientes

En un cliente controlado, utiliza el mecanismo de su sistema operativo o gestor de red para liberar la concesión e iniciar una adquisición nueva. Una simple renovación puede intentar conservar la misma dirección.

No pierdas tu acceso: liberar la dirección puede cortar una sesión remota. Hazlo desde consola o con acceso alternativo.

Para una migración gradual, observa las renovaciones y los tiempos concedidos. Referencia: manual DHCPv4 de Kea.

04

Técnica avanzada ¿Cambiar la IP exactamente en T1?

Es un requisito diferente de cambiar el pool. Un DHCPNAK recibido en el estado correspondiente hace que el cliente abandone la configuración y reinicie la adquisición, según RFC 2131.

REQUEST de renovación ↓ NAK recibido por el cliente ↓ DISCOVER → OFFER → REQUEST → ACK

No hay un hook universal validado en esta guía. No se recomienda falsificar la petición con una dirección artificial para intentar provocar un NAK.

Si el comportamiento nativo no cumple el requisito, un hook específico necesitará desarrollo y pruebas para la versión utilizada.

  • Delimitar las subredes y clientes afectados.
  • Respetar reservas, clases y redes compartidas.
  • Comprobar la concesión y su pertenencia al cliente.
  • Coordinar la decisión con HA y otros hooks.
  • No confirmar una renovación que después se rechace.
  • Preparar observación, registros y reversión.

Estos son requisitos propuestos, no una implementación probada. Consulta la API de hooks de Kea.

05

Sigue el rastro El tráfico cuenta la historia

Realiza la prueba con un cliente identificado y conserva los resultados en privado. Las capturas pueden contener datos e identificadores de tu red.

Captura DHCPv4 / Linux 
sudo tcpdump -ni any -s0 -vvv \
  'udp port 67 or udp port 68'
Evidencias para diagnosticar una migración de pool
Qué observas Qué debes revisar
REQUEST con la IP antigua Puede estar intentando conservarla. Comprueba el estado del cliente y las opciones del paquete.
ACK para la IP antigua Identifica al servidor que responde y revisa su configuración activa, reservas y políticas.
Sin respuesta Revisa logs, selección de subred, conectividad, firewall y relays.
DHCPNAK Comprueba quién lo envía y si el cliente comienza después una nueva adquisición.
ACK del nuevo pool Verifica también máscara, puerta de enlace, DNS y conectividad.

Un log no es una captura: el mensaje “forzando NAK” no demuestra que el DHCPNAK se haya enviado o recibido.

06

Resuelve tus dudas Preguntas frecuentes

¿Debo borrar todas las concesiones antiguas?

No como procedimiento automático. Borrar un registro del servidor no ordena al cliente abandonar inmediatamente su dirección. Diagnostica el caso y prepara una migración controlada.

¿Cambiar el pool reinicia los temporizadores?

No por sí mismo. El cliente sigue los parámetros de su concesión hasta que los actualice mediante DHCP o cambie de estado.

¿Una IP fuera del pool siempre es incorrecta?

No. Kea admite reservas fuera de los pools dinámicos. Un mecanismo de rechazo debe tenerlas en cuenta.

¿Esta página administra mi servidor?

No. Es documentación estática: no se conecta a Kea, no pide contraseñas y no ejecuta comandos. Los botones permiten navegar, copiar texto o descargar archivos.

¿El script fuerza el cambio de IP en T1?

No. Modifica el pool en un archivo local compatible, valida y guarda el cambio si lo autorizas. No instala hooks, no borra leases y no reinicia Kea.

¿Qué hago si necesito revertir?

Restaura la copia correspondiente, valida y aplica la configuración anterior mediante tu gestor. Restaurar el archivo no deshace automáticamente las concesiones que ya se hayan entregado.

07

Tu herramienta de campo Kea Pool Manager

PYTHON 3.8+ LINUX KEA DHCPv4 REVISAR Y PROBAR

Un script para listar pools, previsualizar cambios, validar una configuración candidata y guardar un rango nuevo con copia de seguridad.

No es un hook de renumeración. No fuerza DHCPNAK, no borra concesiones y no recarga ni reinicia el servicio. Revisa el código y pruébalo en laboratorio.

Descargar .py ↓ Revisar código ↗ Leer README ↗

1. Consulta los pools

Descarga el archivo, revisa su contenido y abre una terminal en la carpeta donde lo hayas guardado.

Listar / no modifica el archivo 
sudo python3 kea-pool-manager.py \
  --config /etc/kea/kea-dhcp4.conf \
  --list

2. Previsualiza el rango nuevo

Adapta el ID de subred, el índice del pool y las direcciones. Los índices empiezan en cero.

Vista previa y validación 
sudo python3 kea-pool-manager.py \
  --config /etc/kea/kea-dhcp4.conf \
  --subnet-id 1 \
  --pool-index 0 \
  --range "172.21.0.40 - 172.21.0.70"

3. Guarda cuando estés preparado

Escritura con confirmación 
sudo python3 kea-pool-manager.py \
  --config /etc/kea/kea-dhcp4.conf \
  --subnet-id 1 \
  --pool-index 0 \
  --range "172.21.0.40 - 172.21.0.70" \
  --write

Después debes aplicar la configuración y comprobar el servicio. Guardar el archivo no significa que Kea ya lo esté utilizando.

Compatibilidad y límites de la herramienta

Está orientada a configuraciones locales autocontenidas. Se detiene ante directivas include, config-control no vacío, la biblioteca HA reconocida y el hook t1-renumber anterior. No detecta necesariamente todos los mecanismos externos de gestión o sincronización.

No admite toda la sintaxis extendida posible de Kea, no comprueba si una IP está ocupada y no sustituye la revisión de reservas, clases y arquitectura. Consulta el README antes de utilizarla.
