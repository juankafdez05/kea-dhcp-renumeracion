GUÍA DE ADMINISTRACIÓN · DHCPv4

Cambias el pool.
El cliente conserva su IP.

Entiende qué ocurre con las concesiones existentes al modificar un rango en Kea y cómo preparar, aplicar y verificar el cambio sin confundirlo con una renumeración forzada.

Ver el procedimiento Entender T1 y T2

01. El escenario

Un cliente dispone de una concesión del rango antiguo. El administrador cambia el pool y espera que, al renovar, el cliente obtenga inmediatamente una dirección del nuevo rango.

Ejemplo dentro de 172.21.0.0/24
Pool anterior: 172.21.0.10 - 172.21.0.30
Pool nuevo:    172.21.0.40 - 172.21.0.70
IP del cliente antes del cambio: 172.21.0.20

La distinción importante: modificar un pool no envía por sí mismo una orden al cliente para abandonar la dirección que ya está utilizando.

El pool configurado, el registro de la concesión en el servidor y el estado del cliente son elementos diferentes. No debe deducirse el resultado de una renovación únicamente mirando el nuevo rango.

No se afirma que todas las versiones de Kea renueven una dirección fuera del pool. La respuesta concreta debe verificarse con la versión, configuración y tráfico del entorno afectado. Consulta el manual de Kea.

02. Qué significan T1 y T2

T1 · Renewing

Intentar conservar la IP

El cliente intenta renovar con el servidor que le concedió la dirección. No está solicitando necesariamente una IP distinta.

T2 · Rebinding

Buscar una renovación

Si no logró renovar, el cliente amplía la petición mediante broadcast para intentar obtener respuesta.

Expiración

Dejar de usar la concesión

Si la concesión expira sin renovación, el cliente deja de utilizarla y reinicia la adquisición de configuración.

Según RFC 2131, los valores predeterminados son T1 = 50 % y T2 = 87,5 % del tiempo de concesión. Pueden negociarse otros valores. Fuente: RFC 2131, §4.4.5.

Reducir los temporizadores del servidor no modifica retroactivamente los que un cliente ya recibió. Planifica los tiempos antes de la migración.

03. Procedimiento para cambiar el pool

Ejemplo para un servidor independiente administrado mediante archivos locales y systemd. Adapta las rutas, la unidad y el mecanismo de aplicación a tu instalación.

Antes de empezar: prepara acceso de recuperación y una ventana de mantenimiento. En HA, configuración mediante backend o appliances, utiliza el procedimiento de su gestor.

1. Identifica la configuración efectiva

Confirma qué binario y archivo utiliza realmente el proceso. El nombre de servicio siguiente es solo un ejemplo.

Inventario 
kea-dhcp4 -V
kea-dhcp4 -W
sudo systemctl cat kea-dhcp4-server

Revisa la subred, sus reservas, clases, otros pools, relays y hooks. No publiques credenciales ni configuraciones reales completas en un repositorio público.

2. Guarda una copia de seguridad

Copia local 
sudo cp -a /etc/kea/kea-dhcp4.conf \
  "/etc/kea/kea-dhcp4.conf.bak.$(date +%Y%m%d-%H%M%S)"

Si utilizas archivos incluidos, respalda también los que vayas a modificar. Guarda la copia fuera del repositorio público.

3. Cambia el pool afectado

Dentro de la subred existente, modifica el atributo pool correspondiente. Conserva el ID de subred y los demás atributos. No reemplaces otros pools que sigan siendo necesarios.

Fragmento, no configuración completa 
"pools": [
  {
    "pool": "172.21.0.40 - 172.21.0.70"
  }
]

Comprueba que el nuevo rango pertenece a la subred y no contiene direcciones usadas de forma estática. Revisa reservas que puedan devolver una dirección antigua.

4. Valida antes de aplicar

Validación 
sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf

Utiliza el mismo binario que ejecuta el servicio. Si la validación falla, no continúes. Una validación correcta no demuestra que el proceso activo ya haya cargado el cambio ni que la migración funcione.

5. Aplica y comprueba

Este ejemplo reinicia el servicio y puede interrumpir temporalmente DHCP. Sustituye la unidad por la de tu instalación.

Aplicación en ventana de mantenimiento 
sudo systemctl restart kea-dhcp4-server
sudo systemctl status kea-dhcp4-server --no-pager -l
sudo journalctl -u kea-dhcp4-server \
  --since "5 minutes ago" --no-pager

6. Migra y verifica los clientes

Para un cliente controlado, utiliza el mecanismo de su sistema operativo o gestor de red para liberar la concesión y comenzar una adquisición nueva. Una simple renovación puede intentar conservar la misma dirección.

Hazlo desde consola o con acceso alternativo: liberar la dirección puede cortar tu sesión remota. Para una migración gradual, observa las renovaciones reales y los tiempos concedidos.

Referencia del procedimiento: manual del servidor DHCPv4 de Kea.

04. ¿Y si necesito el cambio exactamente en T1?

Es un requisito diferente de cambiar el pool. Un DHCPNAK recibido en el estado correspondiente hace que el cliente abandone la configuración y vuelva a iniciar la adquisición, según RFC 2131.

REQUEST de renovación ↓ NAK recibido por el cliente ↓ DISCOVER → OFFER → REQUEST → ACK

No hay un hook universal validado en esta guía. No se recomienda falsificar la petición con una IP artificial para intentar provocar indirectamente un NAK.

Si el comportamiento nativo no satisface el requisito, un hook específico necesitará desarrollo y pruebas para la versión de Kea utilizada.

  • Delimitar las subredes y clientes afectados.
  • Respetar reservas válidas, clases y redes compartidas.
  • Comprobar la concesión y su pertenencia al cliente.
  • Coordinar el comportamiento con HA y otros hooks.
  • Evitar confirmar una renovación que luego se rechace.
  • Disponer de observación previa, logs y plan de reversión.

El listado anterior es una propuesta de requisitos, no una implementación probada. Consulta la API de hooks de Kea.

05. Comprueba el tráfico, no solo el log

Captura DHCPv4 en Linux 
sudo tcpdump -ni any -s0 -vvv \
  'udp port 67 or udp port 68'

Realiza la prueba con un cliente identificado y conserva los resultados en un lugar privado. Las capturas pueden contener identificadores y datos de tu red.

Evidencias para diagnosticar una migración de pool
Evidencia Qué revisar
REQUEST con la dirección antigua El cliente está intentando conservarla. Comprueba su estado y las opciones del paquete.
ACK para la dirección antigua Identifica al servidor que responde y revisa configuración activa, reservas y políticas aplicables.
No hay respuesta Revisa logs, selección de subred, conectividad, firewall y relays.
NAK Confirma qué servidor lo envía y si el cliente reinicia después la adquisición.
ACK con dirección del nuevo pool Comprueba también máscara, puerta de enlace, DNS y conectividad del cliente.

Un mensaje del hook indicando “forzando NAK” no demuestra que se haya enviado o recibido un DHCPNAK. Estas comprobaciones son una lista de diagnóstico propuesta; deben interpretarse junto al tráfico y los logs del entorno.

06. Preguntas frecuentes

¿Debo borrar todas las concesiones antiguas?

No como procedimiento automático. Borrar el registro del servidor no ordena al cliente abandonar inmediatamente su dirección. Primero diagnostica el caso y prepara una migración controlada.

¿Cambiar el pool reinicia los temporizadores del cliente?

No por sí mismo. El cliente sigue los parámetros de su concesión hasta que los actualice mediante DHCP o cambie de estado.

¿Una dirección fuera del pool es siempre incorrecta?

No. Kea admite reservas fuera de los pools dinámicos. Un mecanismo de rechazo debe tenerlas en cuenta.

¿Esta página administra mi servidor?

No. Es documentación estática. No se conecta a Kea, no solicita contraseñas y no ejecuta comandos. Los botones solo copian texto.

¿Qué hago si el cambio falla?

Revisa los logs. Si necesitas revertir, restaura la copia correspondiente, valida de nuevo y aplica la configuración anterior con tu gestor del servicio. Restaurar el archivo no deshace automáticamente concesiones ya entregadas.
